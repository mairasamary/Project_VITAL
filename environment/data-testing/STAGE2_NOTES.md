# Stage 2 Design Notes

## Why `forms` is necessary

The captured schema shows that `form_vitals` contains `pid` but no `encounter`. The `forms` table contains both `encounter` and `form_id`. Stage 2 therefore inserts a `form_vitals` row and immediately registers it in `forms`.

## Why Project VITAL validates relationships itself

The selected schema uses indexes such as `pid_encounter`, but the captured CREATE TABLE statements do not declare SQL `FOREIGN KEY` constraints connecting the selected tables.

Therefore:

```text
SQL insert succeeds
```

does not necessarily mean:

```text
relationship is valid
```

This is pedagogically useful for Assignment 4.

## Batch markers

Stage 2 marks synthetic records so they can be safely identified and removed:

- `patient_data.genericname1 = project_vital_batch`
- `patient_data.genericval1 = <batch>`
- `form_encounter.external_id = <batch prefix>`
- `form_vitals.external_id = <batch prefix>`

Students should never use the reset utility against records that were not generated by Project VITAL.

## ID ranges

The first teaching loader uses high numeric PID/encounter ranges for the isolated local course environment. Before any use against a nonempty or shared environment, the ID-allocation strategy must be revisited.

Project VITAL's course Docker environment is the intended target.
